# Risk register

Hazards that the Asili toolchain itself can contribute to in a product built with it, in the
structure of ISO 14971 (hazard → cause → harm → control → residual risk). It is the toolchain's
input to a manufacturer's own risk management file: severity and probability depend on the
product, so they are left to the manufacturer; what is recorded here is how each hazard arises
in the toolchain, which requirements ([requirements.md](requirements.md)) control it, and what
risk remains for the manufacturer to control.

| ID | Hazard (cause) | Possible effect in a product | Controls | Residual risk / manufacturer's action |
|---|---|---|---|---|
| H-1 | The compiler produces code that computes a wrong result (an optimizer or code generator bug). | A wrong output value (actuator command, dose, alarm decision). | REQ-COMP-1 (every function's IR verified), REQ-COMP-2 (optimized = unoptimized on random programs), REQ-NUM-1, REQ-NUM-2 (hand-checked reference results), REQ-TGT-2 (device = build machine). | Testing is not proof: a bug in a construct the tests and fuzzer do not reach can remain, and optimized and unoptimized code share the lowering and code generator. Verify the product's own functions on the target with the product's own tests; keep the toolchain version fixed (see [tool-qualification.md](tool-qualification.md)). |
| H-2 | A control step runs longer than its deadline (an unbounded loop, recursion, allocation, or a call into code without bounds). | A missed control deadline. | REQ-STRICT-1 (strict subset enforced), REQ-STRICT-2 (step bound per call), REQ-FAIL-2 (watchdog). | The step bound counts bytecode steps, not processor cycles, and is computed, not measured. Measure worst-case execution time on the target part (caches, flash wait states, interrupts) and size the watchdog from it. |
| H-3 | Memory runs out or fragments while the product runs. | The program stops at an arbitrary point. | REQ-STRICT-3 (no allocation in strict code), REQ-FAIL-3 (memory limit enters the safe state); on Cortex-M, strict code uses only the stack. | Ordinary (non-strict) code allocates; keep safety functions strict. On a device, size the stack from the `kumbukumbu` bound plus the firmware's own use. |
| H-4 | The runtime crashes (a panic or abort) instead of failing in a defined way. | Outputs left in an undefined state. | REQ-FAIL-5 (no panic paths in the runtime), REQ-FAIL-4 (a fault enters the safe state), REQ-FAIL-1. | The panic hook is verified by inspection only; a fault in the safe state itself cannot be handled by it. The product needs an independent safe state (hardware watchdog, fail-safe output design). |
| H-5 | Code reads or writes memory outside its data (an index out of range, a damaged artifact naming registers that do not exist). | Corrupted state, wrong outputs, crash. | REQ-RUN-1 (index checks), REQ-COMP-4 (bytecode verified on load), REQ-COMP-1. | Indexing is checked at run time unless range analysis proves it in range; a failed check is an error the product must handle (on a device, a non-zero return). |
| H-6 | A damaged, mismatched or substituted artifact is run. | The product runs code other than what was verified. | REQ-COMP-4, REQ-COMP-5 (image bound to its program), REQ-COMP-3 (reproducible builds let a build be checked against its source). | The checks detect accidents, not attacks: they are not cryptographic. Record artifact hashes in the release and verify them on installation; sign artifacts where tampering is a concern. |
| H-7 | A program behaves differently on the target than where it was tested (another architecture, the browser, a device). | A defect that appears only in the field. | REQ-TGT-1, REQ-TGT-2, REQ-TGT-4, REQ-TGT-5 (the same results on every target, checked bit for bit). | `**` on Cortex-M uses `libm` and may differ in the last bit from the build machine: avoid `**` in strict code or verify its results on the device. |
| H-8 | Runaway recursion exhausts the stack. | Crash. | REQ-RUN-2 (call-depth limit is an error), REQ-STRICT-1 (no recursion in strict code). | Ordinary code may recurse to the limit; the limit is a count of calls, not of bytes — keep deep recursion out of products. |
| H-9 | A device export writes into the caller's array (lists are passed by reference on Cortex-M). | The firmware's data changes unexpectedly. | REQ-TGT-3 (callees may not write lists they receive); the header and how-to state the convention. | An exported function that assigns to its own list parameter writes the caller's array — documented; review exported functions for it. |
| H-10 | A safety function is written outside strict code (`#[salama]` forgotten). | None of the strict-code guarantees apply. | `pata jenga` prints every strict function and its bounds. | Process control: the manufacturer's design review must confirm that every safety function is strict. |
| H-11 | A defect in the toolchain is already known but not considered. | As H-1. | The bug tracker (GitHub project "Asili bug tracker") lists known anomalies. | Review open anomalies against the product before each release ([tool-qualification.md](tool-qualification.md), "Known anomalies"). |
